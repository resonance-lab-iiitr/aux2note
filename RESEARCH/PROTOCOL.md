# Research protocol (Claude: read this ONLY in a research mode: R-PLAN, R-BUILD, R-IMPORT, R-ANALYZE, R-SYNTH)

START_HERE.md still rules: one unit of work per session, a new zip after it, no secrets, code beats docs, `Correction:` instead of rewriting.
This file adds the research track. Research answers a question with measurements so the main plan is changed on evidence, not on guesses.

## Objects, ids, files (ids are unique across the whole project)
| Object | Id | Lives in |
|---|---|---|
| Study | S### | `RESEARCH/studies/S###_<slug>/STUDY.md` (fields at the top, `Key: value`) |
| Hypothesis | H### | `hypotheses.csv` in the study (statement, prediction, refuted_if, status, confidence, evidence) |
| Experiment | E### | `experiments/E###_<slug>.md` (card) + `E###_RUNSHEET.md` + script under `scripts/` or `spikes/` |
| Evidence (one run's pack) | V### | `evidence.csv` + `evidence/digests/V###/` (small files only; big files listed by hash, raw stays on the owner's PC) |
| Finding | F-## | `findings.csv` (columns id,finding,evidence,confidence,status,next_action first, then study,hypotheses,runs) |
| Gate (stage decision) | G### | `gates.csv`: pre-registered rule, required experiments, outcome, decision id (D### in DECISIONS.md) |
| Research note | RNOTE_<date>_<HHMM>_S###.md | `RESEARCH/notes/` until folded by R-SYNTH. The file count is the **Research lag** |
| Study report | | `STUDY_REPORT.md` in the study, rewritten at every gate; it is the portfolio document |
| Learning log | | `LEARNING_LOG.md` in the study: concepts, methods, corrected beliefs, reading list (rule 13) |
| Showcase | | `SHOWCASE.md` (narrative, owner's voice) + `showcase/FACTS.md` and `showcase/figures/` (generated by `research.py showcase S###`) |
| Domain annex | | `DOMAIN.md` in the study, copied from `RESEARCH/templates/domains/<name>.md` (project-specific definitions, checklists, figures; `audio` ships) |

Use `python3 tools/research.py` (see its header) for every id-bearing edit: `new-study` (`--depth deep`, `--domain audio`), `new-exp`, `add hyp|finding|gate`, `set hyp|finding|gate|ev|exp`, `ingest`, `import`, `showcase`, `fold`, `status`.
It assigns ids and writes valid CSV; do not hand-edit CSV rows. STUDY.md and experiment cards are edited with normal file edits (keep the `Key: value` lines).

## Rules for everything (they are what makes a result trustworthy)
1. **Pre-register.** Pass rule, Fail rule, Repeats, Changed and the analysis plan are written before the run. Once an experiment is `ready` they are not edited. A wrong rule is fixed by a new experiment card plus a `Correction:` line, never by changing the old one.
2. **One variable.** `Changed:` names exactly one thing. Everything else is `Held fixed:`. If the owner changed more, say so and treat the run as confounded.
3. **Trust the instrument first.** Every study starts `Instrument trust: untrusted` unless it is `n/a`. A calibration experiment (known-good input, expected output) must pass before measure experiments count. While untrusted, all hypotheses and findings are capped at confidence `low` (validate.py enforces). Set `trusted` only when a calibration experiment is analyzed and passed its rule; write which one in STUDY.md "Instrument".
4. **Controls.** A measure experiment names its controls (known-good signal, a minimal script without the app, a second device, a baseline run). When "is it the program or the device?" is the question, a minimal control script is the first experiment.
5. **Runs and what "clean" can prove.** Never a verdict from one run. `Repeats` is at least 3 for a measure. A claim of "clean" or "never happens" is only as strong as the number of clean runs n: failure probability is bounded by about 3/n at 95 % (n=3 gives no useful bound, n=10 about 30 %, n=30 about 10 %). For a phenomenon known to be intermittent, set Repeats to what the claim needs and state the bound in the finding.
6. **Confidence** (the only values): `none` not assessed; `low` one run, or untrusted instrument, or uncontrolled, or plausible only; `medium` at least 3 runs agree and controls ran, one rival explanation still open, or the evidence is retroactive; `high` at least 3 independent runs, instrument trusted, the pre-registered rule met, controls exclude the main rivals (a deterministic fact such as arithmetic may be `high` with n=1 if the finding says "deterministic"). Retroactive evidence (experiments with `Retroactive: yes`) never exceeds `medium`.
7. **Status words.** Hypothesis: open, supported, refuted, inconclusive, superseded. `inconclusive` is a valid, kept result: write which run count or control would settle it. Never turn it into a pass.
8. **Say what you cannot do.** The sandbox has no sound card, no Windows, no way to listen. Claude reads numbers, tables, images and logs. Anything not verified goes under "Limits of this session". Never state a number you did not take from evidence or compute here.
9. **No rewriting history.** Earlier claims, including legacy reports and earlier chats, stay as written; add `Correction:` lines. Negative results are kept.
10. **Research never changes the product.** Research modes write only under `RESEARCH/` plus the control files named per mode. They never edit `CODE/`. Prototypes live in the study's `spikes/`. They may import from `CODE/` read-only and run its tests.
11. **Reads.** Boot files, this file, `python3 tools/research.py status`, the study in scope (STUDY.md, LEARNING_LOG.md, SHOWCASE.md, DOMAIN.md, its CSVs, the experiment cards you work on, digests you need). Never `ARCHIVE/`. Log extra reads in the note.
12. **Size.** One session: at most 3 research questions, 6 hypotheses, 5 experiment cards (R-PLAN); one experiment (R-BUILD); all packs of one experiment (R-ANALYZE); one gate (R-SYNTH). If more is needed, finish what fits and write the rest into the note's Next.

13. **Academic and showcase layer** (the owner uses studies for coursework and a portfolio, so every study must teach and be presentable; nothing here relaxes rules 1 to 12).
   - Every study has `LEARNING_LOG.md` and `SHOWCASE.md` (new-study copies them). Research modes update the learning log (at most 5 new entries per session, each tied to an id from this study, in plain language with a self-check question) and R-SYNTH refreshes the showcase. Claude never marks an entry "understood": only the owner does, after answering the question in his own words.
   - Sources: no invented citations. A reference enters as `unverified`; it becomes `opened` only after a web search / fetch (or the owner) really read it, with a line saying what was checked. If Claude cannot search, it lists topics to look up, not references.
   - `Depth: deep` (set in STUDY.md; default `standard`) adds to R-PLAN: a background paragraph, a statistics plan written before the runs (estimand, n per setting and why, interval or bound, effect size, what counts as noise), an ablation table (one factor per experiment), a data dictionary (metric, unit, formula, script version) and an authorship statement; the report fills section 9 and 10.
   - Showcase claims are only as strong as findings.csv: same confidence word, same ids, limits stated first. A showcase never says "proved" for confidence `low` or `medium`. Negative and inconclusive results are shown as results.
   - Honest authorship: SHOWCASE.md says what the owner did and what the assistant did; Claude cannot hear audio or touch hardware.
   - Project-specific detail goes into the study's `DOMAIN.md` (definitions, environment checklist, standard controls, standard figures, known pitfalls). If a study needs a domain that has no annex, R-PLAN writes one under `templates/domains/` and logs it in the note (it is a template change, allowed because it only adds a file under RESEARCH/templates/).
   - Figures come from scripts in the study's `spikes/` run on evidence, captioned with V ids; never hand-edited.

## Modes
Boot: read START_HERE, STATE, this file; run `python3 tools/research.py status`. The mode comes from START_HERE Step 2.

### R-PLAN (no code): question to experiments
1. Goal from `goal:`, the owner's question or STATE Goal. No study yet: `new-study "<title>" --type investigate|explore|optimize`. Read PROJECT_MAP; open code only to write accurate Procedure steps.
1b. Set `Depth:` and `Domain:` in STUDY.md (ask nothing: `deep` when the owner says coursework / portfolio / academic, else `standard`; domain `audio` for sound work). Copy the learning and showcase files if the study predates them.
2. Fill STUDY.md: research questions (answerable by measurement), why it matters (name the tasks / phases that wait and what changes on yes / on no), Instrument, Environment constants, Threats.
3. Hypotheses with `add hyp`: statement, prediction (what the instrument will show), refuted_if (what would prove it wrong). Investigate studies need at least two rival hypotheses. Optimize studies: a baseline experiment first (`Baseline:` in STUDY.md). Explore studies: the options and the go / no-go criteria go into the gate rule.
4. Stages with a gate each (`add gate`, rule in numbers). Stage 0 is calibration of the instrument unless trust is `n/a`. Detail only the current stage; later stages get a stage line and a gate.
5. Experiment cards with `new-exp` (kind calibration / measure / control / spike / replay). Fill every card field: rules, Changed, Held fixed, Controls, Metrics, Repeats, Confounds, Notes to record, Procedure, Analysis plan. Status stays `planned`.
6. Link to the main plan: add `Gate: G###` to the cards of tasks that must wait for the answer (edit only that line). Do not add, change or cancel tasks here; R-SYNTH does.
6b. Learning log: add the concepts the owner needs to understand this plan (max 5) and, for `deep`, the statistics plan and background in STUDY.md.
7. STATE research fields, one RNOTE (from `RESEARCH/templates/RNOTE.md`), CLOSE.

### R-BUILD: make one experiment runnable
1. The experiment: `exp:` override, else the one `status` names. Read its card and the study's STUDY.md; read code only as needed (log it).
2. Write the script at the card's `Script:` path (prototype / spike code in `spikes/`). It must: record every setting it uses; fail early with a plain message if a device is missing; end by building a result pack with `RESEARCH/lib/rpack.py` (`ResultPack`, metrics named exactly as the card's Metrics); support `--selftest` that runs on synthetic data with no hardware and builds a pack that `rpack.py check` accepts.
3. Run the selftest in the sandbox and show the output. This is the software half of the instrument validation. If a calibration experiment needs hardware, say so: it stays `planned` until the selftest passes, and the part that only the owner can verify is stated in the run sheet as "not verified in the sandbox".
4. Write `experiments/E###_RUNSHEET.md` from `RESEARCH/templates/RUN_SHEET.md` (exact steps and commands, what to send back).
5. `set exp E### status=ready`. From now the rules are locked (rule 1). Update STATE "Awaiting owner". RNOTE, CLOSE. The final chat message tells the owner in at most 5 lines what to run and what to attach.

### R-IMPORT: bring older evidence in (legacy reports, logs, captures, earlier "research directions")
1. Inputs: zips or folders, a `study:` (existing id or `new`). Read their own index first (READ_ME / report / handoff / findings table / direction file). Do not open bulk raw files; `research.py import` copies only text-like files (csv, json, md, txt, log, png, gz) up to 1.5 MB and lists audio, zips and big files by hash. Import per experiment, one `import` call per run folder, so each run keeps its own evidence id. Pick what is evidence; do not import the whole archive blindly (the project zip is attached every session).
2. Create or choose the study. Map: questions to RQs, the old plan to hypotheses and stages (rewritten as in R-PLAN, not copied), known tool defects to Threats and keep `Instrument trust: untrusted`.
3. Register every old test as an experiment card with `new-exp --retroactive` (`Retroactive: yes`; Pass / Fail rule: the original threshold if the old text had one, otherwise "legacy: not pre-registered"). Status `analyzed` only after its evidence is filed (`import`, then `set ev V### analyzed=yes`).
4. Legacy findings: one row each in findings.csv (keep the original id and wording; put nuance in the text, confidence mapped to the enum, status mapped to the enum, `defect` for tool defects). Do not upgrade any confidence.
5. Write `legacy_index.md` in the study: original file, where it lives now (digest path or "raw, owner PC, sha prefix"), which later corrections apply. Keep the old reports' corrections as `Correction:` lines.
6. Retroactive evidence is capped at `medium`.
6b. Learning log and showcase draft: add up to 5 concepts the legacy evidence teaches; write the SHOWCASE.md draft with status `draft` and only claims findings.csv allows.
7. RNOTE, CLOSE. The next session is normally R-PLAN to turn the old plan into stages and gates.

### R-ANALYZE: result packs in, verdicts out (no code, no plan change)
1. For each attached pack: `python3 tools/research.py ingest <pack.zip>`. A damaged pack is refused: say so, ask for a rebuild. A pack with a blank notes.txt is accepted but its runs are capped at `low`; tell the owner.
2. Read the digest files and notes.txt of the new evidence. First the calibration / control rows: if they contradict the measurement, say that before anything else.
3. Compare with the card's Pass and Fail rules exactly as written, run by run. Add one Results row per run (run, setting, metrics, verdict, evidence id). Compute n, min, max, mean across runs of the same setting.
4. When the card's Repeats are reached: `set exp E### status=analyzed` and `set ev V### analyzed=yes` for its runs. If fewer, leave it `ready` and report partial results with no verdict. A passed calibration experiment: edit STUDY.md `Instrument trust: trusted` and name it under Instrument.
5. Update hypotheses (`set hyp`: status, confidence by rule 6, evidence ids, experiments) and findings (`add finding` / `set finding`, each citing V ids and n). A surprise no hypothesis covers becomes a new open hypothesis; a follow-up experiment is proposed in the note's Next, not planned here.
5b. Learning log: add up to 5 entries from what the run showed (a surprise goes into section 4 as belief vs data). Do not mark any entry understood.
6. Report gates that are now ready (`status` shows them). RNOTE, CLOSE.

### R-SYNTH: decide, report, change the plan
1. Read STUDY.md, the CSVs, the Results tables, the unfolded RNOTEs; digests only to verify a number.
2. For each ready gate apply its pre-registered rule to the results: outcome pass / fail / inconclusive (inconclusive means more runs or a new experiment, never a pass). `set gate G### status=decided outcome=<...> decision=D### impact=<...>` and write the decision D### in DECISIONS.md (what, why, rejected alternatives, evidence ids).
3. Rewrite `STUDY_REPORT.md` (all sections, every number cites a V###, limitations honest, reproduction commands). Add a one-line research entry to CHANGELOG (the one exception to "CHANGELOG only in DOC").
4. Change the main plan by evidence: add tasks (card from `TEMPLATE_TASK_CARD.md`, QUEUE line, waves), edit cards, cancel tasks (move the card to `ARCHIVE/retired_tasks/`, replace its QUEUE line with `- cancelled T### | D### | reason`, a line the validator ignores). Update ROADMAP. Cards that waited keep their `Gate:` line (a decided gate no longer blocks).
4b. Refresh `SHOWCASE.md` (headline table, limits, talking points) and run `python3 tools/research.py showcase S###`; update the learning log (max 5).
5. Advance STUDY.md `Stage:` to the next stage (or `Status: closed` after the last gate); update the INDEX line label.
6. `python3 tools/research.py fold` (moves every unfolded RNOTE, so Research lag becomes 0). R-SYNTH writes no RNOTE of its own; the report and the decision are its record. CLOSE.
   Edits allowed: RESEARCH/, QUEUE, task cards, ROADMAP, DECISIONS, CHANGELOG (research line), STATE. Never `CODE/`.

## Closing a research session (replaces CLOSE steps 1 and 2 of START_HERE; steps 3 to 5 are unchanged)
1. STATE: timestamp, Version + 1, Status (READY unless interrupted), "Last completed work" (one line), `Research active`, `Research priority`, `Research lag` (= number of files in RESEARCH/notes), `Awaiting owner` (ids of experiments with Status ready). Leave Doc lag and the unfolded task notes alone: research sessions write no ACTIVE_DOCS/sessions note.
2. One row in USAGE_LOG.
3. Run `python3 tools/validate.py .`, fix every ERROR; run `python3 tools/pack.py .`; deliver the zip; chat message at most 5 lines.

## Result pack and run sheet (what the owner does)
The owner runs a script (or `rpack.py make ...`) and gets `results/E###_<label>.zip`: `manifest.json` (experiment, run label, machine and driver facts, file hashes, metrics), `notes.txt` (the owner's words, per the card's "Notes to record"), small data files. Big recordings are listed by sha256 and stay on the owner's PC, so the project zip stays small. The owner attaches the latest project zip plus the packs and pastes the standard one-line prompt.
